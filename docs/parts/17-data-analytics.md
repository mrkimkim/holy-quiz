# 17. 데이터·애널리틱스·실험

> **한 줄 목적:** 말씀퀴즈의 유일한 차별점인 '명예 리더보드'가 조작 없이 신뢰받고, 광고·구독 매출과 교회 바이럴이 데이터로 증명·개선되며, 종교라는 민감정보를 PIPA 준수 하에 다루면서 교회 DB를 합법적 B2B 자산으로 성장시키기 위한 측정·실험·거버넌스 체계를 정의한다.

> **데이터 파트의 소유권 선언(정렬 근거):** 본 문서는 (1) **재무 계획 기준선**(ARPDAU·DAU/MAU·실수령 구독 ARPU·잔존곡선·LTV 산식, →17.2), (2) **이벤트 택소노미 단일 소스**(`taxonomy.yaml`, →17.4), (3) **MMP/어트리뷰션 스택 조정 오너**(→17.5.1)의 **유일 진실원**이다. monetization·org·client·server·marketing 문서는 위 세 항목에 대해 본 문서 값을 참조·정렬한다(상충 시 본 문서가 우선).

## 17.1 지표 체계 — North Star & KPI 트리

### 17.1.1 North Star 선정과 근거
- **North Star Metric(NSM) = 주간 유효 풀이 문제 수 (Weekly Qualified Questions Answered, WQA)**
- 채택 근거: PRD 제품원칙 '매일의 습관에 얹는다'와 정합. WQA는 (1)습관 형성(반복 세션), (2)교회 대항 점수의 원자재(상위20 주간포인트 합산), (3)광고 노출 기회(20문제=전면 1회)를 동시에 대표하는 유일한 지표. 매출·리더보드·리텐션이 모두 WQA의 하위 파생.
- **'유효(Qualified)'의 정의는 반드시 서버 권위**: 매크로 무효 세션(1.5초 미만 연타), 봇/에뮬레이터, 어뷰징 격리 계정의 풀이는 WQA에서 제외한다. 이 정의가 없으면 NSM 자체를 조작으로 부풀릴 수 있음(→ 17.9 연계).

### 17.1.2 KPI 트리 (NSM 분해)

```
WQA(주간 유효 풀이 수)
├─ WAU(주간 활성 유저)
│   ├─ 신규 유입 = 오가닉 설치 + 유료 UA 설치 + 유효 초대(validated-K)
│   ├─ 활성화율 = 온보딩 완료 × 진단퀴즈 완료 × 첫티어 도달 × 교회등록
│   └─ 리텐션 = D1 45% / D7 28% / D30 18% / WAU:MAU 스티키니스
├─ 유저당 주간 세션 수 (세션/WAU)
│   ├─ 리텐션 훅: 출석연속, 오늘의말씀, 푸시 오픈율
│   └─ 콤보/티어 승급 동기(승급 근접도)
└─ 세션당 문제 수 (문제/세션)
    ├─ 콘텐츠 신선도(재출제율 20% ↓ = 소진 신호)
    ├─ 난이도 적합도(진단 정확도, 이탈률)
    └─ 전면광고 빈도(20문제)의 세션 지속 영향(가드레일)

수익(파생) = WQA → 광고 노출 × ARPDAU + 구독 전환 × LTV
바이럴(파생) = 티어승급/주간결산 → 공유 → 초대 → 유효초대 → 신규 WAU
교회활성도(파생) = 참여 성도 수 × 기여자 다양성 × 주간 기여 지속
```

## 17.2 KPI 가정 검증 — 감도분석 & 손익 역산 (재무 기준선 단일 소스, data 오너)

### 17.2.1 광고 ARPDAU 재산정 (하방 반영)
PRD의 ARPDAU ₩30은 `전면 2.5회/일 × eCPM ₩12,000 × 100% fill × ATT 무영향` 가정. 실무 보정:

| 변수 | PRD 낙관 | Base(권고 기준) | Bear |
|---|---|---|---|
| 전면 노출/DAU | 2.5 | 2.2 (fill 실패·노쇼 반영) | 1.8 |
| Fill률 | 100% | 88% | 75% |
| iOS eCPM(ATT 옵트아웃 반영) | ₩12,000 | ₩8,500 | ₩6,000 |
| Android eCPM | ₩12,000 | ₩10,000 | ₩7,500 |
| **실효 ARPDAU** | ₩30 | **약 ₩18~21** | **약 ₩11~13** |

→ **결론:** ARPDAU는 ₩18~21로 계획하고, ₩30은 상방으로 관리. iOS ATT 옵트인율은 별도 지표로 추적하며(목표 관측 후 설정), 광고 매출의 iOS/AOS 분리 대시보드 필수.

- **ARPDAU 정의 통일(→ finding, monetization/org 정렬):** base ₩18~21은 **전면(interstitial) only** 기준이다. **배너·보상형(2x)은 v1.1 상방 레버로만 가산**하며 base에 선반영하지 않는다. monetization의 **블렌디드 ₩20.5**(전면+배너+보상형)는 base가 아닌 **상방**으로, org의 **₩15**(전면만·보수)는 base 하단으로 각각 정정해 **본 base 범위(₩18~21)로 수렴**시킨다. 세 문서는 동일 정의(전면 base + 배너·보상형 상방)를 참조한다.

### 17.2.2 구독 실수령 반영
`₩3,900 표시가 → 스토어 수수료 15%(소액결제자 대부분 Small Business Program 대상) → 실수령 약 ₩3,315(첫해 15% 가정), 30% 구간 시 ₩2,730`. 부가세 별도(→ monetization/legal). 매출 모델은 **실수령 기준**으로만 산정한다.

- **LTV 잔존곡선 통일(→ finding, monetization/org 정렬):** LTV는 **D5(17.7)의 실측 잔존 코호트**를 단일 기준으로 사용한다(90일 실측 → 외삽 시 동일 곡선 파라미터). '24개월 곡선 잔존합' 또는 '6개월 flat 잔존' 등 **임의 잔존가정을 각 문서가 개별 사용하는 것을 금지**한다. LTV 산식·잔존모델은 본 절이 유일 소스이며 monetization·org의 LTV:CAC 비교는 동일 곡선에서만 유효하다.

### 17.2.3 손익 역산(간이) — '월 매출 2,000만원' 성립 조건 감도표
DAU=MAU×0.25(PRD KPI) 가정. 광고+구독 합산 월매출 목표 2,000만원.

| MAU | DAU | 광고월매출(ARPDAU ₩20) | 구독(1.0%,실수령₩3,315) | 합계 | 목표 대비 |
|---|---|---|---|---|---|
| 100,000 | 25,000 | 약 1,500만 | 약 331만 | 약 1,831만 | 미달(약 92%) |
| 130,000 | 32,500 | 약 1,950만 | 약 431만 | 약 2,381만 | 초과 |
| 100,000 | 25,000 | 광고 ARPDAU ₩30이면 2,250만 | 331만 | 2,581만 | 초과 |

→ **의사결정 근거:** 2,000만원은 'MAU 10만 + ARPDAU ₩20'로는 아슬하게 미달. **레버는 ① ARPDAU를 ₩24 이상으로(전면빈도 실험, 보상형 v1.1) 또는 ② MAU 약 13만.** 구독은 보조(전체의 15~18%)임을 재확인.

- **재무 3문서 reconcile(→ finding 1/9):** DAU/MAU **25%** 기준에서 monetization(base ₩20.5 가정 시 100k에서 겨우 걸침)·org(₩15 가정 시 미달, 180k 필요) 모두 **본 표의 base(₩18~21)로 정렬**하면 100k에서 목표 미달로 수렴한다. 즉 **월 2,000만원 달성엔 MAU 약 13만 또는 ARPDAU ≥₩24 필요**. 이 표를 재무 3문서의 **단일 reconcile 기준이자 월간 비즈니스 리뷰 공통 슬라이드**로 고정하고, 'MAU 10만 도달'과 '월 2,000만원'을 분리 KPI로 명시한다.
- **BEP MAU(→ org 공동):** 손익분기 MAU는 가정 매출이 아니라 **실제 번레이트(org 인건비·SaaS·서버·MMP 비용)** 기준으로 org와 공동 재산정한다(조달 규모 정합).

### 17.2.4 K-factor 정의 분리·게이트 모순 관리
유효초대 3단계 조건(가입+교회등록+20문제완료)은 정당하지만 K를 구조적으로 낮춘다. **초대 전환 퍼널을 단계별로 계측**(초대발송→클릭설치→가입→교회등록→20문제)하여 '어디서 K가 새는지'를 보고, 게이트를 완화하지 않고 **전환 병목(예: 교회등록 이탈)을 온보딩 개선으로 푼다.**

- **gross-K vs validated-K 분리(→ finding 7, marketing/org 정렬):** 
  - **gross-K** = 성장 귀속용. 모든 딥링크 설치(코드리스 자동귀속 포함)를 분자로 하는 총 증폭계수. MMP install/deferred deep link로 계측.
  - **validated-K** = 보상 지급·리더보드 반영용. 유효초대 3단계 게이트 통과분만 분자.
  - **PRD의 'K 0.3'은 validated-K 기준**으로 확정한다. 마케팅 D4의 루프 합산 K(개인초대+브로드캐스트)는 **gross-K**로 간주하고, validated-K는 게이트 통과율(예 gross 0.4~0.5 → validated 0.2~0.3, org 22.6.4와 정합)로 별도 산출한다.
  - **계획 기준선은 보수(validated 0.15)로 잡되 목표(0.3)를 병기**하고, MAU 10만 곡선의 증폭계수(1.18~1.43 범위)를 채택 K로 재산정해 대시(D3)에 노출한다.

## 17.4 이벤트 택소노미

### 17.4.1 명명 규칙 & 원칙
- **형식:** `object_action` snake_case (예: `quiz_question_answered`). 과거형 동사.
- **소스 태그:** 각 이벤트는 `C`(클라이언트 UX) 또는 `S`(서버 권위) 소스로 명시. **점수·포인트·티어·교회점수·초대유효·결제·격리는 반드시 S.**
- **볼륨 관리:** `quiz_question_answered`는 NSM 원자재라 전건 수집(서버). 초고볼륨 `quiz_question_served`는 세션 단위 요약으로 대체해 하위 SDK 비용 절감(→17.5).
- **버저닝:** `schema_version` 프로퍼티로 스키마 변경 추적. 스펙은 Git 관리(**단일 소스: `docs/analytics/taxonomy.yaml`**).

### 17.4.4 이벤트명 정렬 (단일 소스 → client/server 리팩터)
`taxonomy.yaml`의 **canonical 명칭이 유일 소스**다. 현재 파트별 발행명이 상이하므로(client 13.13·server 14.24는 **리팩터 대상**) 아래 매핑으로 정렬한다. 명명규칙은 `object_action` 과거형.

| Canonical (data, 유일) | client 현행 → 정정 | server 현행 → 정정 |
|---|---|---|
| `quiz_question_answered` | quiz_answer → `quiz_question_answered` | attempt_scored → `quiz_question_answered` |
| `quiz_session_completed` | quiz_session_end → `quiz_session_completed` | session_completed → `quiz_session_completed` |
| `tier_promoted` | tier_up → `tier_promoted` | `tier_promoted`(일치) |
| `subscription_started` | subscription_start → `subscription_started` | subscription_state_changed → `subscription_started`(+상태전이는 `subscription_refunded` 등으로 분리) |
| `church_registered` | church_register → `church_registered` | `church_registered`(일치) |
| `invite_validated` | invite_attributed → `invite_validated` | invite_state_changed → `invite_validated`(+귀속은 `share_completed`/`invite_link_created`) |

- **church_id 전송 규칙 명문화(→ finding 16, legal 정합):** church_id를 보유한 이벤트(`church_registered` 등)는 **소스 S(서버)로만 발행**하고 **GA4 등 국외 SDK로 전송 금지**(→17.5.1 민감정보 격리). client `AnalyticsService`는 church_id 보유 이벤트를 국외 SDK로 보내지 않고 **server→BigQuery(서울) 경로로만** 흐르게 구현한다(church_id GA4 전송 시 PIPA §23 민감정보 무동의 국외이전 위반). client·server·marketing은 이 매핑표를 `taxonomy.yaml`에 정렬한다.

> **MMP 방침 정정(→ finding 3/8/11, client W3·marketing·org 정렬):** 초대 자동귀속(deferred deep link)은 성장엔진 K-factor의 계측·귀속 인프라이자 **F8 v1.0 필수 기능**이다(server 14.10.2도 client의 install referrer/deferred deep link가 invite_id를 넘겨준다고 전제). 따라서 기존 '**MMP를 월 UA ₩10M+까지 보류**' 방침을 **F8 자동귀속에 한해 철회**하고, **data가 조정 오너로서 v1 단일 MMP를 출시 전(client 리스크상 W3까지) 확정**한다. 벤더 후보(AppsFlyer/Airbridge/Adjust) 중 **카카오 딥링크·iOS SKAN·원화/KR 정산·비용** 기준으로 **1개**를 선정한다(현재 client=AppsFlyer OneLink, marketing=Airbridge 1순위로 상충 → W3 단일화). 결정된 스택 위에 client 딥링크·server 귀속 계약(install referrer/deferred→invite_id)·**data SKAN 전환값 스키마**·org SaaS 예산을 동시 정렬한다.
>
> **스코프 대안(명시적 선택):** 만약 W3까지 MMP 단일화가 불가하면 **v1은 6자리 코드 수동귀속만 제공하고 자동귀속(F8)을 v1.1로 내리는 스코프 조정**을 명시적으로 결정한다(**기본 권고: v1 자동귀속 유지**). '미결정 채로 착수'는 금지.

**핵심 결정 3가지:**
1. **단일 계측, 이중 싱크 금지(초기):** 이벤트는 `AnalyticsService` 래퍼 → GA4 → 자동 BigQuery 익스포트. Amplitude는 v1에서 보류. 이유: 100k MAU × 월 ~900이벤트 = 약 90M/월로 Amplitude 무료티어 초과. **BigQuery+Looker Studio로 리텐션/퍼널/코호트를 자체 구축**해 비용 0으로 v1을 운영, 셀프서브 탐색 수요가 명확해지면 **큐레이션 이벤트(세션 요약 등)만** Amplitude에 투입.
2. **민감정보 격리 라우팅:** `church_id`·교회명·지역 등 종교 파생 속성은 **국외 SDK(GA4/Amplitude 서버=미국)로 전송 금지.** 교회·리더보드 분석은 전량 BigQuery(서울)에서만. GA4에는 비식별 이벤트만.
3. **초고볼륨 이벤트 분리:** `quiz_question_answered` 전건은 서버→BigQuery(집계용). GA4에는 세션 요약(`quiz_session_completed`)만 보내 GA4/BQ 스트리밍 비용 관리.

### 17.5.2 iOS SKAN/ATT 대응
- ATT 프롬프트는 **가치 선설명 후 노출**(옵트인율↑, → ux/client). 옵트아웃 시 광고 id 미전송 + `consent_ad_id=false`로 태깅.
- **선정된 단일 MMP의** SKAN 4.0 conversion value 스키마 설계: postback 윈도우에 '가입→교회등록→20문제' 마일스톤 매핑(유효초대·활성화와 정렬). SKAN 전환값 스키마는 확정된 MMP 스택 위에서만 정의한다(스택 미확정 시 스키마 파편화 방지).

## 17.8 A/B 실험 플랫폼 & 실험 백로그

### 17.8.1 플랫폼·설계 원칙
- **유저 랜덤화 실험**(온보딩/팝업/가격/광고빈도): Firebase Remote Config + A/B, 버킷을 `ab_experiments`로 전 이벤트 태깅 → BigQuery에서 분석.
- **⚠ 리더보드 규칙은 유저 A/B 불가:** '상위 N(오픈퀘스천#2)'은 같은 리더보드를 공유하는 공정성 특성상 유저 무작위 배정이 불가능. **대안: ① 파일럿 데이터로 오프라인 시뮬레이션(N=10/20/30별 대형/소형 공정성·기여자 breadth·공유율 재현) → ② 정식 출시 후 스위치백(주 단위 N 변경)으로 검증.** 유저 A/B로 착각 금지.
- **가드레일 지표 필수:** 모든 실험은 1차 지표 + 리텐션·언인스톨·세션길이 가드레일 동시 판정. 매출 실험은 리텐션 가드레일 우선.
- **중장년 정서 가드레일:** 자극적 카피·과도 빈도는 정량 승리해도 반려(교회 정서·이탈 리스크). 실험 리뷰에 정성 체크 포함.

### 17.8.2 실험 백로그 (우선순위순)

> **E2 명칭 후보 확정(→ finding 4/15, branding 우선):** 파일럿 A/B 후보를 **'초대왕 vs 이달의 초대(중립)'로 단일 확정**한다. branding(10.10)이 **'전도왕'을 신학 리스크로 배제** 권고했고 법무·branding의 신학 수용성 판단을 우선하므로, marketing(D6)·client(remote config `invite_label`)의 '초대왕 vs 전도왕' 셋업을 **동일하게 정정**한다. '전도왕'을 재도입하려면 legal·branding 수용성 검토를 **파일럿 전 완료**해야 하며, 그 전까지 실험군·`invite_label` 기본값에 '전도왕'을 포함하지 않는다.

> **인터페이스(→ monetization/marketing/ux/content):** E4·E5·E7·E8은 각 파트의 로드맵과 공동 소유. 실험 착수 전 '실험 설계서(가설·지표·MDE·표본·중단조건)'를 데이터 파트가 승인.

### 17.8.3 표본·검정 규약
- 최소검출효과(MDE)와 표본크기는 착수 전 파워계산(α=0.05, power=0.8). 저빈도 지표(구독)는 베이지안 순차검정 허용, 조기중단은 사전 규칙만.
- **오픈퀘스천#1(앱이름)은 A/B 부적합**(설치 전 노출 지점 상이) → 스토어 리스팅 실험 or 광고 크리에이티브 CTR로 대체(→ branding/marketing).

## 17.9 어뷰징 이상탐지 — 지표·경보

교회 대항전은 '우리 교회를 위해' 조작할 강한 사회적 유인을 만든다. 명예 리더보드 붕괴 방지가 데이터 파트의 최우선 신뢰 과제.

### 17.9.1 탐지 신호·지표·임계·조치

| 신호 | 지표 | 임계(초기, 튜닝대상) | 탐지방식 | 조치 |
|---|---|---|---|---|
| 매크로 연타 | 세션 내 응답간격 p50 | < 1.5s 반복 | 준실시간 서버룰 | 세션포인트 무효 + `is_macro_flagged` |
| 다계정 담합 | 동일 device_id당 활성 계정수 | ≥ 3 | 신원그래프 일배치 | 계정군집 검토큐 |
| 디바이스팜/교회부양 | 특정 church로 신규유입 급증 z-score | z ≥ 3 | 일배치 | 교회 기여 홀드 + 검토 |
| 시계조작(출석/연속) | client_ts − server_ts 편차 | > 5분 | 이벤트 수신시 | 출석은 **server_ts만 인정** |

| 초대링 | 초대 그래프 밀집/동일망대 | 커뮤니티 탐지 | 일배치 | 유효초대 무효 + 검토큐 |

### 17.9.2 경보·거버넌스
- **경보 채널:** P1(리더보드 정합 붕괴, 대규모 급증)=즉시 Slack+온콜. P2(군집·초대링)=일 다이제스트+검토큐.
- **검토큐:** qa/ops 공동 운영. 오탐 소명 창구 필수(→ qa/ux 갭: '1.5초 무효'가 지식 뛰어난 권사 오탐 가능 → 무효 시 인앱 안내 + 다음세션 정상 + 재검토 요청 버튼).
- **관리 지표(대시 D1):** 매크로 플래그 세션 비율, 무효 포인트 비율, 검토큐 적체·처리시간, 초대 유효율.

> **인터페이스(→ server/qa):** 서버는 요청서명·재전송방지·루팅탐지·서버권위 점수(→ server 파트)를 제공하고, 데이터 파트는 사후 이상탐지·군집분석·재계산 검증을 담당. 두 계층 모두 필요(예방+탐지).

## 17.10 교회 DB·활성도 자산화 & B2B 데이터 제품 준비

### 17.10.1 교회 활성도 스코어(모델)
```
ChurchActivityScore(주간) =
  0.35 × 정규화(참여 성도수)
  + 0.25 × 정규화(주간 유효 풀이수)
  + 0.20 × 기여자 다양성(1 − 지니계수)      # 소수 캐리 페널티
  + 0.20 × 4주 참여 지속(연속 활성 주 비율)
```
- 규모리그(개척/중형/대형) 내 상대정규화로 대형교회 인원우위 상쇄. `agg_church_weekly`에 적재.

### 17.10.2 B2B(목회자 대시보드·데이터 제품, v2 대비) — 사전 준비
- **v1에서 준비할 것(제품 아님, 데이터 기반):** 교회 레벨 집계 마트, 활성도 스코어 시계열, 참여 성도수·연속출석 분포(개인 비식별). 목회자에게 유의미한 뷰의 후보를 미리 축적.
- **⚠⚠ 최우선 법무 게이트(→ legal, high 갭):** 종교·교회소속은 **PIPA §23 민감정보**. B2B '자산화'는 **① §23 민감정보 별도 명시동의 + ② 수집·이용 목적에 'B2B/목회자 제공'을 사전 명시 + ③ 제3자 제공(§17)·목적외이용(§18) 동의** 없이는 **위법(과징금·서비스중지, 목표 자체 무효화 리스크)**. 
- **데이터 파트의 방어 설계:**
  - **개인식별 성도 데이터는 절대 B2B로 제공하지 않는다.** 교회 레벨 **집계·k-익명(최소 N=10)만.**
  - 동의 스코프를 **레이어링:** 앱 이용(리더보드 노출) 동의 ≠ B2B 제공 동의. B2B 동의는 별도·옵트인·철회가능.
  - B2B 목적 태그를 `dim_user.consent_b2b`로 관리, 미동의 유저는 집계에서도 기여 제외(또는 익명 합산만).
  - 목적외이용 감사로그(누가 어떤 목적으로 조회했는지) 보존.
- **온보딩 동의 항목 정합(→ finding 14, ux/client/legal):** `consent_b2b`가 실제로 수집되려면 **ux 온보딩 동의 화면(O2)과 설정>동의 이력에 'B2B/목회자 제공(목적외) 별도 선택 동의' 항목이 반드시 포함**되어야 한다(현재 ux 12.3.1 O2는 이 항목 누락). 이 동의는 **거부해도 서비스 이용 가능**하도록 필수 항목과 시각 분리하고, server가 필요한 동의 목록을 내려주는 데이터 기반 동의화면(client 13.10)과 정합시켜 legal 문구를 확정한다. 항목 누락 시 v1에서 심어야 할 B2B 동의가 실제 화면에서 빠져 자산화가 위법이 된다.

> **결정 권고:** v1은 **자산 축적(집계 데이터·동의 인프라)까지만**, 실제 B2B 판매/제공은 legal 승인·동의 확보 전까지 **불가**로 못 박는다. '교회DB 해자'는 시딩 출처 합법성(→ 17.12·ops 갭)과 동의 없이는 자산이 아니라 부채.

## 17.11 데이터 거버넌스·프라이버시 준수 (법무 연계)

### 17.11.1 민감정보(종교) 처리 — PIPA §23 (high 갭 해소)
| 항목 | 설계 |
|---|---|
| 별도 동의 | **교회 기능 이용 시점(교회 등록 직전)의 선택 동의**로 '종교(교회소속)=민감정보' 별도 동의 화면(일반 약관과 분리). **온보딩 진입 필수 게이트로 두지 않으며**, 미동의 시 교회 기능만 미제공하고 **개인 퀴즈는 무동의로 이용 가능**(PIPA 강요·번들 금지 원칙 정합, legal 19.3·client 13.10과 일치) |
| 강화보호 | church_id·종교파생 속성 **국외 SDK 전송금지**, BigQuery 서울 리전, 컬럼레벨 접근통제 |
| 처리방침 | 처리방침에 종교 항목·목적·보유기간·B2B 목적 명시(→ legal) |
| 최소수집 | 교리·교단 세부는 수집 안 함(PRD도 교리 출제 금지와 정합) |

> **정합 확인(→ finding 2, ux O2):** 데이터 파트 기준(개인 퀴즈는 무동의 이용 가능)은 legal(19.3)·client(13.10)와 일치한다. **ux 온보딩 O2가 '종교 동의 필수·미동의 시 진행 불가'로 게이팅하는 부분은 위 기준으로 수정 필요**(종교 동의는 교회 등록 직전 선택 동의로 이동).

### 17.11.2 라이프사이클·정보주체 권리 (high 갭 해소)
- **동의 관리 플랫폼(경량):** 동의 항목별 상태·타임스탬프·버전을 `consent` 테이블로 관리, 전 이벤트에 `consent_*` 스냅샷 태깅. 미동의 이벤트는 파이프라인 진입 차단(수집 단계 게이팅). **동의 항목 세트 = 필수(약관·개인정보) / 종교민감(교회등록 직전 선택) / 선택(마케팅·야간·국외이전·`consent_b2b`)**. server가 이 목록을 내려주는 데이터 기반 동의화면과 정합(→ 17.10.2, client 13.10).
- **탈퇴 정합성 규칙(→ server/monetization 공동):**
  - 개인식별 데이터: 탈퇴 후 지체없이 파기/익명화(법정 보존분 제외).
  - **포인트·티어:** 개인 순위에서 제거. **교회 주간 기여**는 이미 확정된 과거 주차는 **익명 합산으로 잔존(리더보드 이력 정합)**, 미확정 당주는 제거 여부를 규정으로 확정(→ openQuestion).
  - **초대 귀속:** 초대자-피초대자 링크는 익명 집계만 잔존, 개인식별 제거.
- **권리 대응:** 열람·정정·삭제·처리정지 요청 처리 SLA와 셀프서비스(인앱) 설계 → ops CS 연계.
- **국외이전 동의(§28-8):** AdMob/Firebase(GA4)/SKAN/**선정 MMP** 등 국외 SDK 이전 항목·국가·목적 고지·동의. iOS ATT 광고식별자 동의와 별개로 관리.

### 17.11.3 미성년·야간푸시 (high/medium 갭)
- **연령게이트:** 가입 시 생년 수집 → 만14세 미만은 법정대리인 동의 없이는 수집 차단, **아동 맞춤형(행태) 광고 비활성**(광고 SDK child-directed 플래그), **미성년 실명 전국 리더보드 노출 금지**(닉네임/마스킹). 데이터 파트는 `is_minor` 세그먼트로 광고·노출 분기.
- **야간 광고성 푸시(21~08시):** 새벽기도 리마인드=광고성 소지 → 야간 별도 수신동의 없으면 발송 금지. `push_opened.sent_hour`로 준수 모니터링, E9 실험으로 정보성 재프레이밍.

### 17.11.4 저작권 데이터 표기(→ legal/content high 갭)
- F1 근거구절·F9 원문은 **개역개정 본문의 축자 복제·전송**. PRD의 '라이선스 불필요' 단정은 위험. 데이터 파트는 **표시된 구절의 출처·버전·표시횟수를 로깅**해 성서공회 협상·정산 근거 데이터를 미리 확보(사후 라이선스 협상 시 사용량 증빙).

## 17.12 데이터 품질 (테스트·모니터링·시딩 검증)

- **dbt 테스트:** not_null(user_id/church_id/points), unique(응답 idempotency key), accepted_values(tier/category/**entry_type**), 관계무결성(fct→dim), **커스텀: 서버 포인트 원장 vs 리더보드 재계산 일치**, **커스텀: `agg_church_weekly` 합산이 `is_church_eligible=true`만 포함(보상형/신고보상 제외 회귀)**.
- **볼륨/신선도 모니터:** 이벤트 유입량 급감·급증 이상탐지, 파이프라인 지연 경보.
- **교회 시딩 검증(→ ops/data medium 갭):** 대형교회 500~1,000개 시딩의 **출처·수집방식 합법성**을 데이터 파트가 검수. 장소검색 API 스크래핑=약관위반 리스크 → **공개·합법 소스(자체 입력, 파트너 교회 제공, 공개 교단 총회록)로 레코드화**하고 `source`·`verified_by`·`collected_at` 메타 필수. verified 기준(주소+교단+홈페이지 2개 교차확인) 정의.
- **교회 엔티티 관리(→ server medium 갭):** 병합/분립/폐업/이전/개명 이벤트를 `dim_church` SCD2 + 매핑테이블로 관리(동일교회 판정 규칙). 교회변경 월1회 시 기존 주간기여 이전 규정을 데이터 정합 관점에서 명세.

## 17.14 콘텐츠 소진·난이도 캘리브레이션 데이터 루프 (content 연계)

- **소진 조기경보(→ content high 갭):** 헤비유저 하루 100문항+ 소비 vs 월 증분 500 갭을 D6 대시로 상시 노출. **지표: 유저 P90의 미출제 잔량, 주간 재출제율.** 재출제율이 목표 20%를 초과 상승하면 증분 요구를 자동 산정해 content에 전달(예: '이 소비속도면 헤비유저는 8주 내 소진, 월 증분 900 필요').
- **난이도 재라벨링 루프(→ content, 지표 통일):** 문항별 실측 **raw 정답률(p-value)** 로 쉬움/보통/어려움 재분류. **단일 임계 표(→ finding 6, 격리·재라벨 통합):**

  | 판정 | 지표(통일) | 임계 |
  |---|---|---|
  | 자동격리 | raw `correct_rate` | < 15% (시도≥50) |
  | 재라벨: 쉬움 | raw 정답률 | > 80% |
  | 재라벨: 보통 | raw 정답률 | 40~80% |
  | 재라벨: 어려움 | raw 정답률 | < 40% |

  content(18.7.2)의 정규화 밴드(≥0.75/<0.45)는 위 **raw 밴드로 정정**한다. 진단 10문제 배정 알고리즘(E3)도 이 실측치로 주기 보정. 콜드스타트(저자 추정 4:4:2)를 출시 4주 후 실측 기준으로 교체. 정규화(실력 보정)는 표본 확보 후 v1.1+ 고도화 후보(단일 지표는 v1에서 raw).

## 17.16 의존성/인터페이스 요약

- **server:** 서버권위 점수·요청서명·재전송방지·루팅탐지 제공; Pub/Sub 이벤트 발행(**14.24 발행명을 canonical로 리팩터**, 17.4.4); 리더보드 재계산 대조; 교회 엔티티 SCD; server_ts 기준 출석; **`point_ledger` `entry_type`/`is_church_eligible` 산출(보상형·신고보상 교회점수 제외)**; deferred deep link→invite_id 귀속 계약. 월요 00시 리셋 부하 계측 협업.
- **client:** `AnalyticsService` 단일 래퍼로 택소노미 준수(**13.13 발행명을 canonical로 정정**, church_id 국외SDK 미전송); 동의·ATT 게이팅; 확정 MMP 딥링크 SDK 연동; 오프라인/약전파 시 이벤트 큐잉·광고 실패 태깅.
- **legal:** PIPA §23 민감정보·§17/18/28-8 동의 설계 검토; 종교 동의=교회등록 직전 선택 동의(온보딩 필수 게이트 아님); 저작권(성서공회) 협상; 미성년·야간푸시·B2B 목적 동의; 처리방침 문구.
- **content:** 소진 경보·증분 요구 수신; 난이도 재라벨링 데이터(**raw 정답률 단일 지표·격리15% 정렬**); F9 자동검증 정확도 지표.
- **monetization:** 실수령 기준 매출 모델(**ARPDAU base ₩18~21·LTV 단일 잔존곡선 정렬**); 구독 영수증검증 이벤트; 가격·광고빈도 실험 공동; 보상형 교회점수 제외 가드레일.
- **marketing:** 확정 단일 MMP 기반 SKAN 어트리뷰션; gross-K/validated-K 정의 정렬; 종교 타깃 광고정책 제약 반영한 CPI 측정; 초대 명칭 실험(**branding 확정 후보 초대왕 vs 이달의 초대**).
- **ux/design:** 온보딩·팝업·접근성(색약/스크린리더) 실험; 오탐 소명 UX; **온보딩 O2에 B2B 별도 동의 추가·종교 동의 게이트 완화**.
- **qa/ops:** 어뷰징 검토큐 공동 운영; CS 채널 데이터 연계; 시딩 출처 검수; 보상형/신고보상 교회점수 제외 회귀 케이스.
- **branding:** 앱이름(#1)은 A/B 불가 → 스토어 리스팅/광고 CTR 대체 측정; 초대 명칭 신학 수용성 판단 우선(전도왕 배제).
- **org:** 파일럿 성공기준·BD 리드타임 데이터화; ARPDAU/DAU/MAU 재무 기준선·BEP MAU(실비) 정렬; 단일 MMP SaaS 예산.
